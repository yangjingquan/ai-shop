# 团购功能设计

日期：2026-07-25

## 背景

当前商城包含 Spring Boot 多模块后端、Vue 3 商家后台和原生微信小程序。小程序首页已有“限时会场”静态模块，其中“团购商品”目前只是展示卡片。商品、购物车、订单、支付回调和商家发货链路已经存在，订单状态目前覆盖待支付、待发货、待收货、已完成、已取消。

本次目标是在小程序增加可用的团购 MVP：商家可在商品维度配置是否参加团购、团购价格和几人成团；用户从首页“限时会场”-“团购商品”进入团购商品列表，支持开团/参团；支付成功后未满员订单为“待成团”，满员后订单变为“已成团”。

## 范围

本期包含：

- 商家后台商品新增/编辑支持团购配置。
- 小程序首页“团购商品”入口跳转到真实团购商品列表。
- 小程序支持团购商品列表、商品详情开团/参团、团购确认下单。
- 后端新增团购活动配置、团实例和参团成员模型。
- 支付成功后计入参团人数，满员自动成团。
- 团有效期默认 24 小时，超时未成团标记为拼团失败/待退款并释放库存。
- 小程序和商家后台订单列表/详情展示团购相关状态。
- 商家只能对已成团的团购订单发货。

本期不包含：

- 微信自动退款接口、退款回调和退款证书配置。
- 邀请海报、二维码裂变、佣金或分销。
- 多个团购商品合并下单。
- 普通商品和团购商品混合购物车下单。
- 阶梯团购价、单独团购库存、按 SKU 配不同团购价。

## 关键决策

- 使用独立团购模型，而不是把团状态塞进订单或只按商品累计人数。
- 团购下单限定为单个团购商品，可以选择 SKU 和数量，但一次团购订单只归属一个团实例。
- 只有支付成功的订单才计入参团人数，未支付订单不占团名额。
- 团购有效期默认 24 小时。
- 超时未成团后，本期只标记“拼团失败/待退款”，不自动调用微信退款。

## 数据模型

### 商品表扩展

在 `product` 增加团购展示和下单配置字段：

- `is_group_buy`：是否参加团购，`1` 是，`0` 否。
- `group_buy_price`：团购价格。
- `group_buy_required_count`：几人成团。

商品实体、保存请求、列表 VO、详情 VO 和前后台 API 类型同步增加这些字段。

校验规则：

- `is_group_buy=1` 时，`group_buy_price` 必须大于 0。
- `is_group_buy=1` 时，`group_buy_required_count` 必须大于等于 2。
- 建议校验团购价格不高于商品最低 SKU 售价，避免配置失误。
- `is_group_buy=0` 时，团购价格和成团人数可清空或按默认值持久化。

### 团实例表

新增 `group_buy_group`：

- `id`
- `merchant_id`
- `product_id`
- `leader_user_id`
- `required_count`
- `paid_count`
- `status`：`0=待成团`，`1=已成团`，`2=拼团失败/待退款`，`3=已取消`
- `expire_at`
- `formed_at`
- `created_at` / `updated_at` / `deleted`

索引：

- `(product_id, status, expire_at)` 用于查询可参团列表。
- `(status, expire_at)` 用于超时任务扫描。
- `(merchant_id, status)` 用于后台管理和订单联动。

### 参团成员表

新增 `group_buy_member`：

- `id`
- `group_id`
- `user_id`
- `order_no`
- `status`：`0=待支付`，`1=已支付`，`2=已取消`，`3=待退款`
- `paid_at`
- `created_at` / `updated_at` / `deleted`

约束：

- `order_no` 唯一，保证订单和参团记录一一对应。
- 可增加 `(group_id, user_id, deleted)` 索引，便于限制同一用户重复参团策略。本期默认允许同一用户不同订单参团，但每个订单只能绑定一个成员记录。

### 订单表扩展

在 `order` 增加团购关联字段：

- `order_type`：`0=普通订单`，`1=团购订单`。
- `group_buy_group_id`：团实例 ID，可空。

订单状态新增：

- `5=待成团`
- `6=已成团`
- `7=拼团失败/待退款`

状态含义：

- 团购订单创建后仍为 `待支付`。
- 团购订单支付成功但未满员时为 `待成团`。
- 团满员后为 `已成团`。
- 超时未成团后为 `拼团失败/待退款`。
- 已成团订单发货后进入现有 `待收货`，后续继续复用确认收货和完成流程。

## 后端接口设计

### 商品接口

复用现有商家商品接口：

- `POST /api/merchant/products`
- `PUT /api/merchant/products/{id}`
- `GET /api/merchant/products`
- `GET /api/merchant/products/{id}`

请求和响应增加团购字段。

公共商品接口增加团购筛选：

- `GET /api/public/products/page?isGroupBuy=1`

该筛选只返回上架且已开启团购的商品。

### 团购接口

新增小程序团购接口，路径建议放在 `server/shop-wx-app`：

- `GET /api/wx/group-buy/products`：团购商品分页，可按关键词或分类筛选。
- `GET /api/wx/group-buy/products/{productId}`：团购商品详情，包含可参团团列表。
- `POST /api/wx/group-buy/groups`：开团并创建待支付订单。
- `POST /api/wx/group-buy/groups/{groupId}/join`：参团并创建待支付订单。
- `GET /api/wx/group-buy/groups/{groupId}`：团详情，用于订单详情或分享落地页展示。

开团/参团请求包含：

- `productId`
- `skuId`
- `quantity`
- `addressId`
- `remark`

开团时后端创建团实例、订单和参团成员。参团时后端对团实例加行锁，校验团状态、未过期、未满员，再创建订单和成员。

### 支付回调

复用现有 `OrderPaymentServiceImpl.handlePaidCallback`，按订单类型分支：

- 普通订单：保持现有逻辑，支付成功后变为 `待发货`。
- 团购订单：支付成功后参团成员变为已支付，订单先变为 `待成团`。
- 对团实例加锁后重新统计已支付人数。
- 如果已支付人数达到 `required_count`：
  - 团实例变为 `已成团`。
  - 团内所有 `待成团` 订单变为 `已成团`。
- 如果未达到人数：
  - 团保持 `待成团`。

支付回调继续保持幂等：支付流水唯一约束仍是第一层保护，团购成员和团实例更新必须在事务内基于当前状态判断。

### 超时任务

新增定时任务，例如 `GroupBuyTimeoutJob`：

- 扫描 `status=待成团` 且 `expire_at < now` 的团。
- 对团实例加锁。
- 如果仍未满员：
  - 团实例变为 `拼团失败/待退款`。
  - 已支付成员变为 `待退款`。
  - 关联订单变为 `拼团失败/待退款`。
  - 释放订单库存并重算商品库存。
- 未支付订单仍可按现有订单超时逻辑取消，或在团失败时同步取消。

订单列表/详情：

- `待成团` 订单展示团过期时间和当前人数。

## 并发与一致性

- 开团创建团实例和订单在同一事务内完成。
- 参团时对 `group_buy_group` 使用行锁，防止超卖团名额。
- 支付回调处理团购状态时再次锁定团实例，基于已支付成员数量判断是否成团。
- 库存仍沿用现有下单扣库存策略；团失败时释放库存。
- 支付回调、团超时任务、用户取消可能同时发生，所有状态更新必须以当前状态为条件，保证幂等。

## 错误处理

新增或复用业务错误码：

- 团购商品不存在或未开启团购。
- 团已满员。
- 团已过期。
- 团状态不可参团。
- 团购价格配置无效。
- 成团人数配置无效。
- 团购订单状态不允许当前操作。

小程序端对这些错误用 toast 或订单详情状态刷新处理，不在前端自行推断最终状态。
